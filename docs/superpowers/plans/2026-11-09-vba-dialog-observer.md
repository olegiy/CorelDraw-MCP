# Независимый наблюдатель ошибок VBA: план внедрения

> Статус на 9 ноября 2026 года: пользователь поручил выполнить план. Реализован самостоятельный observe-выпуск с изолированными Windows-тестами; живое профилирование и action-расширение не объявляются выполненными. Работа проведена последовательно с циклом «падающий тест → минимальная реализация → проверка»; отдельный навык `executing-plans` не требуется. Установка и коммиты не выполнялись. Фактический результат задач указан в разделе 7; исходный полный чек-лист ниже сохранён для последующего live/action-этапа.

**Цель:** обнаруживать блокирующие диалоги Visual Basic независимо от занятого STA-исполнителя; после проверки принадлежности заданию закрывать только поддержанные ошибки компиляции и возвращать достоверную диагностику без повторного выполнения мутаций.

**Архитектура:** Node.js управляет двумя независимыми процессами: существующим COM-worker и новым наблюдателем Windows. Наблюдатель использует Win32, не обращается к CorelDRAW COM/VBE, не изменяет документы и не устанавливает hooks в приложение. Первое включение — только диагностика; действия разрешаются отдельным режимом после проверки реальных диалогов CorelDRAW 27.

**Стек:** Node.js 24, TypeScript, Windows PowerShell 5.1, C# через существующий подход `Add-Type`, Win32 Unicode API; без новых npm-зависимостей и без зависимости от внешнего agent-desktop MCP.

**Основание:** текущие `docs/architecture.md`, `AGENTS.md`, `src/executor.ts`, `src/jobs.ts`, `powershell/worker.ps1`, `powershell/CorelAutomation.psm1` и приведённый ниже проект решения.

## 1. Текущее поведение и границы задачи

- `powershell/CorelAutomation.psm1:459` перехватывает ошибки выполнения через VBA harness. Это не перехватывает ошибки компиляции и не гарантирует отсутствие модальных окон при настройках VBE, прерывающих обработанные ошибки.
- `powershell/CorelAutomation.psm1:484` запускает Compile через команду 578. Вызов `Execute()` может не вернуться до закрытия окна. Диагностика `COMPILATION_FAILED` и `compiler_location` собирается уже после этого вызова.
- `src/executor.ts:179` удерживает один pending job до соответствующего результата или потери worker. Это необходимо сохранить.
- `src/jobs.ts:221` по дедлайну ставит `timed_out`, но не отменяет COM и не освобождает исполнитель. Поздний достоверный результат сейчас может уточнить статус; `deadline_exceeded` остаётся свидетельством истёкшего срока.
- `powershell/CorelAutomation.psm1:586` сериализует операции и cleanup через `Local\CorelDrawMcp_v27`.
- `corel_get_job` читает сохранённый отчёт без COM и должен продолжать работать при заблокированном worker.
- В исходном плане отмечена ошибка VBA 440 у `VBProjects.Remove` во время предыдущей очистки; при этой проверке она повторно не воспроизводилась. Наблюдатель её не исправит: устранение причин ошибок API, удаление оставшихся проектов и автоматическое исправление пользовательского VBA — вне этой задачи.
- На момент подготовки плана уже изменён `webhost/tests/launcher_browser.mjs`. Этот файл не относится к задаче; его изменения не трогать.
- Наблюдение, включённое только перед `Compile.Execute()`, пропускает возможные блокировки в `VBE`, `Projects.Create`, `AddFromString`, активации pane и cleanup. Пассивное наблюдение нужно запускать после получения identity приложения, до первого обращения к VBE. Подключение к COM и получение самой identity остаются вне гарантированного покрытия; не обещать обнаружение всех модальных окон.
- `Invoke-Vba` вызывается также из экспорта и измерения. Один job может иметь несколько VBA-вызовов; handshake должен находиться в общей функции, иметь отдельное поколение на каждый вызов/фазу и не ограничиваться двумя публичными VBA tools.
- `worker.ps1` сейчас читает stdin синхронным `Console.ReadLine()` как в основном цикле, так и в `validate_json`. Дополнительное ожидание ответа нельзя ограничить одним Node-таймером: нужен один постоянный читатель stdin с маршрутизацией поздних ответов.
- `docs/verification.md` — архив версии 0.1.0 и ссылается на `docs/verification-0.2.0.md`. Новые результаты добавлять в актуальный incremental-отчёт, не переписывая архивные свидетельства.

## 2. Проект решения

### Рассмотренные подходы

1. Проверки в текущем STA-worker: минимальные изменения, но во время заблокированного COM-вызова не исполняются. Не решают основную проблему.
2. Независимый Windows-процесс с адресными Win32-вызовами: продолжает работать при блокировке COM, не зависит от активного окна. **Рекомендуемый вариант.**
3. Внешняя GUI-автоматизация с глобальными клавишами либо перезапуском CorelDRAW: затрагивает пользовательский сеанс и добавляет зависимость. Для штатного восстановления не использовать.

### Режимы и выпуск

Предлагаемый параметр запуска: `CORELDRAW_MCP_VBA_OBSERVER=off|observe|compile-errors`.

- `off` — текущее поведение; аварийный откат без изменения заданий.
- `observe` — рекомендуемый режим первого выпуска: обнаружение и локальная диагностика без нажатий.
- `compile-errors` — отдельное расширение после подтверждения профиля и поведения адресного действия. В первом observe-выпуске это зарезервированное значение отклонять при старте с понятным сообщением «режим пока не поддерживается»; не принимать его с молчаливым переходом в observe. Разрешать явно только в сборке с прошедшим gate задачи 4.
- Значение по умолчанию первого выпуска — `observe`. Неизвестное значение отклонять при запуске, а не трактовать как разрешение действовать.
- Это параметр хоста, не аргумент отдельного MCP tool и не новая система пользовательских разрешений. Передачу через launcher проверить; штатный запуск не должен незаметно терять выбранный режим.
- Node передаёт выбранный режим worker в служебной части команды вне пользовательского `args`. В `off` нет запуска observer, новых COM-getters для identity и ожиданий observer handshake; это проверить отдельным тестом. Откат режима применяется к новому процессу сервера после штатного drain, не перезапускает принятый job и не снимает блокировку старого worker.
- Конкретный путь запуска панели: `CorelMcp.start()` → `OwnedStdio` → `restricted_environment()`. Сейчас системный allowlist отбрасывает `CORELDRAW_MCP_VBA_OBSERVER`, а explicit `extra` допускает только `CORELDRAW_MCP_RUNS`. Добавить адресное разрешение и проверку значений для нового параметра; запрет других переменных, включая legacy config и секреты, сохранить. Проверить также прямую установленную регистрацию Codex без переустановки.

**Порядок выпуска:** задачи 1 (изолированные fixtures), 2, 3, 5 и observe-часть задачи 6 образуют самостоятельный завершённый результат. Live-профилирование из задачи 1 и задача 4 — отдельная ветка с собственным gate; отсутствие доступа к live-сеансу или отрицательная атрибуция не блокируют observe-выпуск. Ни один синтетический fixture не подтверждает профиль CorelDRAW.

### Жизненный цикл

1. Node запускает наблюдатель заранее и получает `ready` с версией протокола. Cold start PowerShell/`Add-Type` имеет отдельный бюджет 10 с; тайм-аут означает degraded, а не ожидание без конца. Завершение observer не означает завершения COM-задания.
2. Worker получает mutex, подключается к приложению и до VBE получает `$script:Corel.AppWindow.Handle`. Context7 для API 27 подтверждает путь `Application.AppWindow.Handle`; опубликованная сигнатура `Handle` — signed Int32. Фактическую typelib и преобразование проверить до реализации. В IPC передавать каноническую строку HWND; отрицательный Int32 нормализовать с сохранением битов, не превращать через `abs()` и не предполагать, что getter возвращает Int64. Добавить тесты старшего бита и round-trip.
3. Worker сообщает контекст job/приложения для **пассивной** фазы до `Assert-VbaIdle`/VBE. Observer независимо проверяет PID/start time, TID, desktop/session и снимает baseline. Сканирование ограничено проверенным процессом и его проверяемыми связями; при недоступности identity — degraded без глобального поиска окон «Visual Basic» по сеансу.
4. После создания и выбора временного GMS worker отправляет `observer_prepare` с job ID, `handshake_id`, фазой и именем проекта. Node назначает новое поколение и случайный token, отправляет `arm` и ждёт `armed`. Только затем отвечает `observer_ready` с effective mode. Если arm не удался, безопасный fallback возможен в observe/off; в будущем compile-errors он допустим только при доказательстве, что action lease не выдавался либо уже отозван с подтверждённым drain. Нельзя выдавать разрешение на автоматическое действие по одному факту получения prepare или продолжать Compile после неоднозначного тайм-аута активации.
5. Worker выполняет Compile. Пока COM заблокирован, observer обнаруживает кандидатов, а Node сохраняет безопасную сводку. Существовавшие в baseline окна тоже видны в диагностике, но запрещены для action. Опрос и журнал не занимают COM mutex.
6. После возврата Compile worker всегда отправляет `observer_finish` для текущего `handshake_id`, включая ветку исключения. Node отзывает lease и ждёт `disarmed`/drain; ответ содержит отдельный приватный итог фазы, а не вывод из публичных счётчиков. `compile_error_confirmed` возможен только при доказанной атрибуции, не по заголовку, исчезновению окна или `dismissed > 0`.
7. При подтверждённой compile error worker не запускает Main, возвращает `COMPILATION_FAILED`, сохраняет GMS и исходную ошибку. При недоступности observer в observe существующий путь может продолжиться после конечного handshake timeout: этот режим никогда не отправляет сообщений действия. В off observer-ветка полностью пропускается.
8. В будущем `compile-errors` Main разрешён только после доказанного окончания действий и завершения фазы. Если action мог быть отправлен, а drain/результат неизвестен, тайм-аут или убийство observer не доказывают отмену. Не переходить к Main, изменяющему COM-cleanup или следующему заданию на основании такого тайм-аута. Без проверенного решения этой гонки gate задачи 4 не пройден; первый выпуск остаётся observe-only.
9. `preparing_vba`, `executing_vba` и `cleanup` наблюдаются пассивно. После disarm compile-фазы при необходимости открыть новое пассивное поколение до следующего потенциально блокирующего вызова. Отдельные VBA-вызовы экспорта/измерения получают собственные поколения. Никакого автоматического End/Reset/Continue/Debug.
10. После фактического результата worker и cleanup Node отправляет observer `stop`, получает `stopped` с закрытым журналом и подтверждает выход; только затем фиксирует финальную сводку и завершает pending. В первом выпуске один observer обслуживает один job со всеми его фазами; следующий job получает новый процесс. Сбой observer сам по себе не удерживает уже завершённую observe-операцию бессрочно: после отзыва lease можно завершить только свой observer и подтвердить его выход. Неизвестный исход действия в будущем compile-errors обрабатывается отдельно по пункту 8.

MCP EOF и потеря Node — разные случаи. При закрытии MCP-транспорта живой Node запрещает новые задания, отзывает активные действия, продолжает пассивную диагностику и drain принятой операции; worker не убивается. При EOF управляющего канала observer, смерти точного Node/worker identity или истечении lease никакие новые действия не разрешены. Node поддерживает lease командой `renew` (например, каждые 500 мс, TTL 2 с по монотонным часам observer); сама живость PID не подтверждает отзывчивость владельца. Контроль stdin/expiry не должен ждать окончания сканирования или записи журнала. Возобновить истёкший token нельзя: нужно новое поколение, причём для уже принятой мутации автоматического replay нет.

### Ограниченный handshake и владение каналом

- В worker должен существовать ровно один читатель stdin на всё время процесса. Небольшой C#-адаптер читает поток в фоне, ограничивает буфер/очередь и доставляет записи основному STA-потоку; COM остаётся только на STA. Нельзя заводить новый `ReadLine`/`Task.Run` на каждое ожидание и оставлять его после timeout: он может поглотить следующее задание или ответ `json_validation`.
- `observer_prepare`/`observer_finish` и ответы коррелируются по версии, job, уникальному `handshake_id`, поколению и ожидаемому типу. Worker отбрасывает устаревшие служебные ответы через тот же dispatcher, в том числе когда уже вернулся к основному циклу. Позднее `armed` после истёкшего prepare немедленно отзывается Node и не активирует действия.
- Конечный бюджет каждого рабочего handshake — 2 с, включая запись/ожидание ack. В observe timeout приводит к безопасному продолжению и degraded, EOF — к штатной обработке потери канала; в off handshake отсутствует. Пути finish/finally не должны маскировать primary error или создавать повторный вызов Compile/Main.
- Наблюдатель тоже не может одновременно блокироваться на stdin и сканировать окна. Его читатель получает команды независимо; один последовательный dispatcher владеет lease и действиями, с приоритетом disarm/stop/expiry. Никаких PowerShell scriptblocks, исполняемых из C#-потока без runspace.
- Лимит 64 КиБ относится к observer JSONL и служебным observer-сообщениям. Не переносить его на существующий worker-протокол: `validate_json` уже переносит VBA JSON до 1 МиБ до экранирования. Совместимость основного формата и его допустимых размеров проверить отдельно.

### Что считать своим диалогом

**PID, заголовок Visual Basic, имя класса `#32770` и время появления — только признаки кандидата, не доказательство принадлежности конкретному заданию.** Пользователь может открыть другое окно в том же процессе, а именованный mutex не блокирует ручные действия.

Действие допускается только при одновременном выполнении всех условий:

- lease принадлежит текущему job/generation, worker жив, фаза — `compiling`, mutex был получен worker;
- PID вместе со временем создания процесса, desktop/session и цепочка владельцев совпадают с проверенным приложением/VBE;
- окно отсутствовало в baseline, появилось после arm, подходит под проверенный профиль CorelDRAW 27 и локали;
- доступные признаки редактора однозначно связывают компиляцию с созданным `CorelMcp_<id>`; способ этой связи должен быть доказан исследовательским этапом, а не предположен;
- структура controls и действие соответствуют проверенному шаблону ошибки компилятора, без выбора Save/Yes/Continue;
- непосредственно перед действием повторно проверены lease, identity HWND/PID/start time, владелец и структура controls; окно не исчезло и не было заменено.

Если имя проекта/контекст не наблюдаемы независимо от заблокированного COM или доказательство неоднозначно — `requires_operator`, без клика. Поддельное окно может копировать признаки; это защита от случайного вмешательства, не security boundary против кода в том же пользовательском сеансе.

Заголовок главного окна VBE, выбранный проект до Compile и совпадение PID сами по себе не доказывают текущий проект при ручном вмешательстве. В read-only результате различать «кандидат в процессе приложения во время job» и «подтверждённая compile error этого проекта». Потерянный owner-chain, недоступные controls и неизвестная локаль дают неполное наблюдение, а не уверенную классификацию. Без hooks невозможно обещать обнаружение каждого краткоживущего окна и каждого переиспользования HWND между опросами. Внутри job не отправлять вторую попытку на уже использованный HWND при неоднозначной identity; новый generation не снимает этот запрет.

### Действия и ограничения

- Только адресное подтверждение ошибки компиляции по проверенному control ID/структуре через ограниченный `SendMessageTimeoutW`. Конкретное сообщение фиксируется после исследования диалога и fixture-тестов.
- Не использовать `HWND_BROADCAST`, `SendKeys`, глобальные Enter/Escape, поиск кнопки только по координатам или по заголовку.
- Никаких `Application.Quit`, kill CorelDRAW/worker, автоматического Reset VBE и изменения режима Error Trapping.
- Сохранение, экспорт, лицензирование, MsgBox пользовательского макроса, чужие диалоги и непроверенные локали не закрывать.
- Один action attempt на подтверждённую идентичность окна; не более 3 попыток суммарно на job, включая несколько VBA-вызовов. Timeout доставки означает неизвестный исход, а не разрешение повторить. Отдельно проверить исчезновение исходного окна; ручное закрытие не считать `dismissed` наблюдателем. Выход observer не отменяет уже доставленное сообщение.
- Предлагаемые стартовые бюджеты: интервал опроса 250 мс; один Win32-вызов ≤250 мс; весь проход ≤1 с, не более 64 кандидатов/128 controls на диалог и owner-chain глубиной ≤16; handshake 2 с; 100 записей событий на job; 16 КиБ UTF-8 на совокупный текст одного диалога; запись JSONL ≤64 КиБ после экранирования; журнал ≤8 МиБ с резервом для завершающей записи о truncation. Ограничить также очереди, stderr, незавершённую строку и число повторных одинаковых ошибок. Опрос 250 мс не является гарантией обнаружения за 250 мс. При переполнении отозвать action lease и явно сообщить truncation/degraded.
- `GetWindowTextW` не даёт общего чтения controls другого процесса. Разрешённые текстовые controls читать ограниченным `WM_GETTEXT` через `SendMessageTimeoutW`, без предварительного неограниченного `WM_GETTEXTLENGTH`; не читать весь редактор/исходники. Тайм-аут/пустой ответ не заменять догадкой. Не применять `SMTO_NOTIMEOUTIFNOTHUNG`, который снимает ограничение ожидания; использовать проверенные флаги и pointer-sized P/Invoke. Эти правила опираются на документацию Win32, но конкретные controls и сообщение действия ещё не подтверждены (источники в разделе 6).
- Ошибка/зависание наблюдателя приводит к `degraded`, отзыву lease и предупреждению. Не освобождает COM-slot, не превращает job в success/failed. Node может завершить только собственный зависший процесс наблюдения после отзыва lease, но не worker или CorelDRAW.
- Если наблюдатель недоступен до Compile, worker получает явный ответ `observe_only/unavailable` и может продолжить существующий путь без автоматического закрытия при условиях fallback из жизненного цикла. Ошибка observe-наблюдения не должна создавать новое бесконечное ожидание handshake; uncertain action в будущем compile-errors имеет отдельный gate.

### Контракт диагностики

Добавить необязательное поле `vba_observer` в `Job` и `WorkerResult`:

- `schema_version`: `1`;
- `mode`: `off | observe | compile-errors`;
- `state`: `starting | observing | degraded | stopped`;
- `detected`, `action_attempted`, `dismissed`, `requires_operator`: неотрицательные счётчики;
- `last_code`: фиксированный код либо отсутствует;
- `events_truncated`: boolean;
- `artifact`: только проверенный путь внутри каталога задания либо отсутствует.

Коды: `VBA_DIALOG_DETECTED`, `VBA_DIALOG_DISMISSED`, `VBA_DIALOG_REQUIRES_OPERATOR`, `VBA_OBSERVER_UNAVAILABLE`, `VBA_OBSERVER_PROTOCOL_ERROR`, `VBA_OBSERVER_LEASE_LOST`, `VBA_DIALOG_ACTION_UNCERTAIN`. `last_code` — только этот enum; произвольные строки и raw ошибки запрещены.

Node — единственный владелец итоговой сводки. На границе IPC проверять enum, версию, конечные safe-integer counters, boolean и путь; не копировать неизвестные ключи из observer/worker. `off` не запускает процесс, при этом может публиковать нулевую сводку `mode=off,state=stopped`; старые reports без поля остаются корректны. В observe `action_attempted=dismissed=0` при любых входных событиях.

Внутренние события содержат job/generation/token и монотонный `sequence`; raw token не пишется ни в публичные данные, ни в журнал. Дубликат sequence не увеличивает счётчики, старый generation/job не меняет сводку. `detected` считает уникальных кандидатов, а не проходы опроса; `requires_operator` — уникальных кандидатов, для которых нужно вмешательство, без вывода о принадлежности проекту. Финальный `WorkerResult.vba_observer` формирует executor из уже накопленной Node-сводки. При merge использовать проверенные накопительные значения без сложения двух снимков; счётчики и `events_truncated` не уменьшаются, отсутствие поля не стирает данные callback. Терминальный `stopped` не означает отсутствие прежней деградации: сохраняются `last_code`/предупреждение. Итог фазы для worker передаётся отдельно от публичной сводки.

Сырые данные окна хранить отдельно в ограниченном `vba-observer.jsonl` внутри run directory: job ID, generation, фаза, время, identity, наблюдённые controls, текст и результат действия. Не выводить raw text в MCP stdout, обычный `run.log`, technical.jsonl или диагностический экспорт. Не передавать его модели автоматически. Не создавать скриншоты. Текст — непроверенные данные, не инструкции. Технические логи сохраняют allowlist; проверить отсутствие утечек ключей, исходников и путей.

Журнал не должен записываться параллельно разными владельцами. Node — единственный писатель `report.json`; наблюдатель — единственный писатель своего журнала. При перезапуске observer не открывать журнал прежнего живого писателя; в первом выпуске не перезапускать observer во время job. I/O failure не освобождает COM-slot. Имя журнала задаёт Node, путь лежит непосредственно в проверенном run directory; проверять links/reparse до открытия в C# тоже, не доверять строке пути из события. Нельзя считать предварительную Node-проверку доказательством безопасного последующего открытия в другом процессе.

Для `Executor.run` добавить необязательный четвёртый callback `observerUpdate?: (summary: VbaObserverSummary) => void`; существующие fixture executors остаются совместимыми. `JobManager` сохраняет обновления callback, даже когда worker не отвечает. Финальная сводка объединяется с уже накопленной, а не обнуляет её. `corel_get_job` не запускает никаких дополнительных обращений к приложению.

Публиковать только изменения сводки с ограниченной частотой, не добавлять raw event в `record()`/stderr и не переписывать отчёт на каждом пустом проходе. Ошибка callback/записи остаётся диагностикой, не должна вызывать `lost()`/reject текущего COM-задания. После передачи финального результата executor в JobManager сводка замораживается; поздний callback не меняет завершённый job и следующее задание. До этой передачи executor завершает остановку observer и merge последних подтверждённых событий. `ArtifactStore.prune()` сохраняет версию, режим, счётчики, state/code/truncation в компактном report, удаляя `artifact`, раз журнал удалён. `diagnosticSummary()` экспортирует только ту же безопасную проекцию без локального пути. Текущий код собирает обе структуры вручную, поэтому простого добавления поля в `Job` недостаточно.

Наблюдатель не определяет outcome операции: закрытие окна не доказывает отмену или отсутствие изменений. `timed_out` сохраняет занятость; `unknown` не повторяется. Поздний результат worker обрабатывается по существующему контракту, без сброса `deadline_exceeded`. Первичная ошибка worker и ошибки cleanup сохраняются отдельно от событий наблюдателя.

## 4. Основные риски и проверка проекта

1. **Нет доказательства принадлежности окна заданию.** Задачи 1 и 4: обязательный gate, иначе observe-only.
2. **Гонка между завершением Compile и кликом.** Задачи 2–4: поколения lease, disarm/drain handshake, повторная проверка identity.
3. **Завис сам наблюдатель или Windows UI-вызов.** Задачи 2–3: bounded Win32-вызовы, supervisor, отзыв lease; COM-job не считается завершённым.
4. **Скрытое выполнение после runtime-диалога.** Задача 4: никакого автоматического runtime End/Reset/Continue, primary outcome только от worker.
5. **Ложный успех после дедлайна либо потеря диагностики.** Задачи 3 и 5: отдельная сводка, сохранение deadline_exceeded, поздние результаты и I/O-failure тесты.
6. **Поздний ответ съедает следующий job/JSON-валидацию.** Задача 3: единственный stdin-reader, dispatcher и реальный fixture PS 5.1; таймер Node этого не решает.
7. **Невидимое изменение режима или потеря сводки.** Задача 5: точечный env allowlist панели, проекции diagnostics/prune и совместимость исторических reports.
8. **Live-тест зависает либо затрагивает прежние диагностические проекты.** Задача 6: явный интерактивный сценарий, отсутствие kill fallback, cleanup по ledger точных identities.

По результатам проверки устранены пропуски ранних VBA-фаз, stdin timeout/late replies, передачи env панели, финализации журнала и проекций сводки. Неизвестными остаются независимая атрибуция реального окна проекту и безопасное завершение адресного действия при timeout; эти вопросы блокируют только action-расширение и не считаются решёнными текстом плана.

## 5. Критерий готовности

Минимальный завершённый результат — рабочий независимый observe-режим с тестами и видимой диагностикой блокировки. Автоматическое закрытие считается готовым отдельно: только для доказанно принадлежащих заданию ошибок компиляции CorelDRAW 27, с проверенным восстановлением worker и отсутствием вмешательства в пользовательские окна. Если такое доказательство недоступно, результат честно ограничивается наблюдением и инструкцией оператору.

В отчёте будущего внедрения отдельно указать: выполненные автоматические проверки, skipped сценарии, результаты живого observe и результаты action gate. Отсутствие live-профиля нельзя превращать в положительный результат; `compile-errors` до прохождения gate остаётся недоступен. Изменение только этого плана не является свидетельством прохождения тестов реализации.

- Context7, библиотека `/websites/community_coreldraw_sdk_api_draw`, запрос по API 27: подтверждены [Application.AppWindow](https://community.coreldraw.com/sdk/api/draw/27/p/application.appwindow?lang=cs) и [AppWindow.Handle](https://community.coreldraw.com/sdk/api/draw/27/p/appwindow.handle?lang=cs), сигнатура `int Handle { get; }`. ## 7. Журнал внедрения observe

Реализованы `VbaDialogObserver.cs`, `JsonLineChannel.cs`, `vba-observer.ps1`
и Node supervisor. Read-only adapter отдельно проверен на чужом процессе
с настоящими Win32 dialogs/controls, Unicode, owner-chain, baseline Save/MsgBox,
ручным закрытием, потерей fixture и зависшим UI. Клики/закрытие/reset отсутствуют
в production-адаптере. Ограничения чтения и независимый watchdog действуют
даже при заблокированном основном потоке observer.

Worker использует одного stdin-reader; реальный PS 5.1 fixture подтвердил
последовательность timeout → поздний observer reply → JSON validation →
следующий job без потери записи. Observer-события сохраняются в отчёте при
timed_out и не завершают COM pending. Исторические reports, late result,
request_id, protected prune, безопасный diagnostics и env allowlist панели
сохранены. Файлы worker/observer ищутся относительно проекта, новых npm-пакетов нет.
